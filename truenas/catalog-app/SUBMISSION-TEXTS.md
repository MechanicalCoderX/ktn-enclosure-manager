## 1. The issue — opened as [#5599](https://github.com/truenas/apps/issues/5599)

**Title:** `App proposal: ktn-enclosure-manager (community train)`

**Body:**

> ### What it is
>
> A web enclosure manager for SAS disk shelves attached to TrueNAS SCALE,
> validated end to end against an EMC KTN-STL3.
>
> TrueNAS gates its built-in enclosure UI behind iX hardware
> (`truenas.is_ix_hardware → False`, `enclosure2.query → []`), so *View
> Enclosure* shows "Enclosure Unavailable" on a community system with a
> third-party shelf. This fills that gap without patching middleware, spoofing
> hardware identity, or touching the WebUI.
>
> It shows a physical drive-bay map keyed by *(enclosure logical id, SES slot)*,
> per-bay disk identity and ZFS state, chassis telemetry from `sg_ses`, and can
> light a bay's IDENT LED to find the right drive.
>
> - Source: <https://github.com/MechanicalCoderX/ktn-enclosure-manager>
> - Image: `ghcr.io/mechanicalcoderx/ktn-enclosure-manager` (public, multi-arch)
> - Licence: MIT
>
> ### What I want to check before opening a PR
>
> **The one unusual ask is a `/dev/sg*` device at `rw` — and the `w` is for
> exactly one command.** Every telemetry read runs `sg_ses --readonly` on an
> `O_RDONLY` fd, where the kernel's per-opcode filter refuses write-class
> commands outright; measured, a `:r` grant serves every page the app reads.
> The `w` exists solely for SEND DIAGNOSTIC — the IDENT LED, the app's single
> write and its reason to exist. It addresses the enclosure processor, not
> disk data. `CAP_SYS_RAWIO` was tested and is **not** required, so it is not
> requested.
>
> Otherwise it is unremarkable: not privileged, keeps the default AppArmor
> profile, no host path mounts, and drops every capability except
> `SETUID`/`SETGID`, used once by `setpriv` to drop the web process to uid 1000.
>
> Is a community-train app allowed to ask for a device node like that? If yes I
> will open the PR; if not, it installs fine via Install-via-YAML and I will
> leave it there.
>
> ### Disclosure
>
> The app and its catalog packaging were written with substantial LLM
> assistance. The hardware behaviour it depends on was measured on a real
> shelf, not assumed.
